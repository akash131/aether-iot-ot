# Platform gaps

What this product needed from the Aether platform and did not find, and
how it works around it. None of these change the platform; each is a
proposal for the platform team.

| # | Gap | Impact | Workaround in this product |
|---|---|---|---|
| 1 | **Service tokens cannot write to peer products.** A tenant-scoped service token of this product carries read permissions on every product (`policy.firewall:read`, `policy.private_access:read`, `policy.branch:read`, …) plus its own scopes (`svc.iot:nodes`, `nodes:*`), observed in the e2e run; Aether Private Access creates privileged approvals with `policy.private_access:create` and Aether Firewall upserts identity bindings with `policy.firewall:update`. `register-service --scopes` covers `svc.<product>:nodes` and `svc.endpoint:enroll` only. | Reading the branch inventory and Private Access sessions works with the service token; creating JIT grants in Private Access and identity bindings in the firewall is refused (403) in a default deployment. | Integrations sit behind traits with fallbacks: without a usable broker the product keeps its own JIT windows, session records and supervision (`LocalAccess`); refused firewall pushes are logged, retried and reported in `GET /api/v1/integrations`. The calls are implemented and tested against in-process fakes (`tests/remote.rs`). Proposal: cross-product scopes such as `svc.private_access:grant` and `svc.firewall:bindings`. |
| 2 | **No product-defined node artifact sets.** Node manifests carry only platform policy artifacts; product configuration that is not a policy (zones, group memberships, approved exceptions, active queries) cannot be distributed through `/node/config`. | Edges need a second, product-specific configuration channel. | The edge fetches a hashed snapshot from this service (`GET /api/v1/node/snapshot`, ETag, content hash verified, tenant checked) next to the platform manifest, persists both and applies them atomically. Proposal: product artifacts in the node manifest. |
| 3 | **Node-to-product calls go direct.** The platform gateway (`/svc/iot`) proxies console traffic; whether it proxies node-token calls to products is not part of the documented contract. | Edges need network reachability to the product (or the gateway path). | `IOT_CONTROL_URL` defaults to `<platform>/svc/iot` and can point at the product directly (the e2e test does). |
| 4 | **No query API for signals.** `POST /api/v1/signals` exists, but there is no documented way to read the signals a product posted. | The e2e test verifies risk signals through the auto-created workloads (`GET /api/v1/workloads`). | — |
| 5 | **Approval decisions are polled.** `GET /api/v1/approvals?state=…&since_version=` is per approval (`version` 1 = requested, 2+ = decided), so there is no global cursor; there is no push notification to the requesting service. | Decisions reach the product on the next worker cycle (5 s by default). | The worker lists decided approvals and also looks up each pending request directly. Proposal: approval decisions on the event bus or a global sequence. |
| 6 | **Event relay and unknown tenants share one platform client.** A product database used by several environments relays events of tenants unknown to the platform; the platform answers `401 unknown tenant`, which the kit relay backs off per tenant. | None in production; in shared test databases the relay needs several cycles. | The e2e test uses a dedicated product database. |
| 7 | **No platform UI for product dashboards beyond metadata.** Dashboards and wizards are declared with `MetaDashboard`/`MetaWizard`; rendering depends on the console. | The volume's UI requirements are met through metadata and data APIs; screen rendering is the console's. | Coverage marks the policy editor UI (section 103) as `platform`. |
