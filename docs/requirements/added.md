# Authored requirements (AE-IOT)

Requirements added from the parity research against the leading commercial IoT/OT security products. The source volumes leave these behaviours unspecified or only implied; each one is implemented and traced like the volume requirements (`docs/requirements/coverage.tsv`). Sources are cited only as URLs.

| ID | Area | Requirement | Sources |
|---|---|---|---|
| AE-IOT-0001 | baseline | Network baseline learning runs in a learning mode that completes automatically when the rate of newly learned behaviour falls below a threshold, or after a fixed window, and can be completed or reset manually. | <https://technicaldocs.nozominetworks.com/products/n2os/topics/learning.html> <https://learn.microsoft.com/en-us/azure/defender-for-iot/organizations/how-to-manage-individual-sensors> |
| AE-IOT-0002 | anomaly | An anomaly can be acknowledged as learned, which adds the observed behaviour to the device baseline so the same behaviour no longer alerts. | <https://learn.microsoft.com/en-us/azure/defender-for-iot/organizations/how-to-manage-the-alert-event> |
| AE-IOT-0003 | anomaly | Devices designated as scanners (authorised scanning tools) do not raise scan anomalies; the designation is an explicit, audited asset attribute. | <https://learn.microsoft.com/en-us/azure/defender-for-iot/organizations/device-inventory> |
| AE-IOT-0004 | inventory | Device records discovered through several identifiers (MAC, hostname, serial, client id, TLS fingerprint) are consolidated into one asset; consolidation and splitting are explicit operations with evidence. | <https://learn.microsoft.com/en-us/azure/defender-for-iot/organizations/how-to-investigate-sensor-detections-in-a-device-inventory> <https://www.armis.com/blog/armis-centrix-release-24/> |
| AE-IOT-0005 | classification | Classification confidence is expressed as tiers (high, medium, low) with documented thresholds, and the tier gates automatic policy assignment. | <https://docs.paloaltonetworks.com/iot/iot-security-admin/get-started-with-iot-security/iot-security-overview/device-identity-and-confidence-score> |
| AE-IOT-0006 | segmentation | Segmentation policy recommendations are generated per device group from the learned behaviour of high-confidence member devices only, and are reviewed before activation. | <https://docs.paloaltonetworks.com/iot/iot-security-admin/manage-iot-security/policy-recommendations> |
| AE-IOT-0007 | active | Each safe active query is enabled per tenant and query type, and honours blackout windows during which no query runs. | <https://docs.tenable.com/OT-security/Content/OT/ActiveQueries.htm> |
| AE-IOT-0008 | active | Active queries exclude restricted address ranges, categories and device types, are limited per target per day, require approval above safe risk or for safety-sensitive devices, and are rate limited on the edge. | <https://docs.tenable.com/OT-security/Content/OT/ActiveQueries.htm> |
| AE-IOT-0009 | baseline | Network learning and process-variable learning run independently, so process learning can be restarted without discarding the network baseline. | <https://technicaldocs.nozominetworks.com/products/n2os/topics/learning.html> |
| AE-IOT-0010 | baseline | Written process values are learned as per-variable ranges and values outside the learned range raise anomalies. | <https://technicaldocs.nozominetworks.com/products/n2os/topics/process-variables.html> |
| AE-IOT-0011 | inventory | Administrators define assertions over the inventory in a bounded expression language; assertions are evaluated continuously and violations are listed and alertable. | <https://technicaldocs.nozominetworks.com/products/n2os/topics/assertions.html> |
| AE-IOT-0012 | segmentation | Zones with security levels and the conduits between them (observed zone-to-zone communication with protocols and highest operation class) are first-class objects of segmentation. | <https://developer.cisco.com/docs/cyber-vision/#!groups> <https://www.isa.org/standards-and-publications/isa-standards/isa-iec-62443-series-of-standards> |
| AE-IOT-0013 | baseline | Baselines are snapshotted before every change and a snapshot can be compared with the current baseline (edges added/removed, operation classes raised, value ranges changed). | <https://developer.cisco.com/docs/cyber-vision/#!baselines> |
| AE-IOT-0014 | inventory | Administrators save inventory views (filters, expression, columns) and share them. | <https://developer.cisco.com/docs/cyber-vision/#!presets> |
| AE-IOT-0015 | vulnerability | Vulnerability findings can be acknowledged with a mandatory reason (risk acceptance), resolved and reopened; acknowledgement is audited. | <https://learn.microsoft.com/en-us/azure/defender-for-iot/organizations/how-to-work-with-threat-intelligence-packages> <https://docs.tenable.com/OT-security/> |
| AE-IOT-0016 | vulnerability | Use of cleartext credentials (Telnet, FTP, HTTP Basic, SNMP communities, MQTT/AMQP passwords) is reported as a finding without retaining the credential. | <https://technicaldocs.nozominetworks.com/products/n2os/topics/vulnerabilities.html> |
| AE-IOT-0017 | risk | Risk factor weights and thresholds are tunable per tenant within validated bounds; every score lists the contributing factors. | <https://www.armis.com/blog/armis-centrix-release-24/> <https://claroty.com/industrial-cybersecurity/threat-detection> |
| AE-IOT-0018 | risk | An operational impact score (device criticality, safety sensitivity, site criticality) is computed separately from likelihood and combined into a remediation priority. | <https://claroty.com/industrial-cybersecurity/threat-detection> |
| AE-IOT-0019 | classification | Device identity is multi-dimensional: category, type, vendor, model, operating system and firmware are classified with separate confidences. | <https://docs.paloaltonetworks.com/iot/iot-security-admin/get-started-with-iot-security/iot-security-overview/device-identity-and-confidence-score> |
| AE-IOT-0020 | inventory | Assets follow an explicit lifecycle (discovered, active, inactive, merged, decommissioned); inactivity is detected automatically and decommissioning removes the device from policy. | <https://www.armis.com/blog/armis-centrix-release-24/> |
| AE-IOT-0021 | remote | Remote access to OT assets is granted only for just-in-time windows with a maximum length and advance limit; sessions cannot start outside the window and are ended at its end. | <https://claroty.com/industrial-cybersecurity/secure-access> |
| AE-IOT-0022 | remote | Vendor principals (external maintainers) request access themselves or through automation; the asset owner approves in the approval inbox and the requester can never approve their own request. | <https://claroty.com/industrial-cybersecurity/secure-access> |
| AE-IOT-0023 | remote | Credentials of target devices are held by the access broker (privileged consoles); vendors never receive them. | <https://claroty.com/industrial-cybersecurity/secure-access> <https://github.com/akash131/aether-private-access> |
| AE-IOT-0024 | remote | Administrators see live sessions and can terminate any session immediately; revocation of a request ends its sessions and the broker grant. | <https://claroty.com/industrial-cybersecurity/secure-access> |
| AE-IOT-0025 | remote | Session recordings are referenced by metadata with a SHA-256 integrity digest, size and duration; recording content stays with the broker. | <https://claroty.com/industrial-cybersecurity/secure-access> |
| AE-IOT-0026 | inventory | The inventory exports to CSV and JSON with the same filters as the list, with formula-injection neutralisation. | <https://learn.microsoft.com/en-us/azure/defender-for-iot/organizations/how-to-investigate-sensor-detections-in-a-device-inventory> |
| AE-IOT-0027 | inventory | Data-quality diagnostics show classification conflicts, ambiguous identities and stale assets so administrators can resolve them. | <https://www.armis.com/blog/armis-centrix-release-24/> |
| AE-IOT-0028 | anomaly | Alerts are de-duplicated per device and kind, counted, and can be acknowledged or resolved; tuning (learned behaviour, scanner designation) suppresses known-good activity. | <https://learn.microsoft.com/en-us/azure/defender-for-iot/organizations/how-to-accelerate-alert-incident-response> |
| AE-IOT-0029 | segmentation | Temporary, specific segmentation exceptions (devices or groups, protocol, port, highest operation class) need approval by someone other than the requester and expire automatically within 30 days. | <https://docs.paloaltonetworks.com/iot/iot-security-admin/manage-iot-security/policy-recommendations> |
| AE-IOT-0030 | anomaly | Engineering operations (program download/upload, firmware update, configuration changes) are detected per protocol and attributed to the initiating station. | <https://learn.microsoft.com/en-us/azure/defender-for-iot/organizations/alert-engine-messages> |
| AE-IOT-0031 | anomaly | Controller mode changes (stop, run, restart, cold/warm start) raise high-severity anomalies. | <https://technicaldocs.nozominetworks.com/products/n2os/topics/alerts.html> |
| AE-IOT-0032 | segmentation | Quarantine is enforced through the enforcement points (edge decisions and nftables drops, firewall identity bindings) and is reversible and audited. | <https://docs.paloaltonetworks.com/iot/iot-security-admin/manage-iot-security/iot-security-integrations> |
| AE-IOT-0033 | anomaly | Programming or write operations from stations not learned as engineering stations for the controller are flagged as unauthorised engineering activity. | <https://learn.microsoft.com/en-us/azure/defender-for-iot/organizations/alert-engine-messages> |
| AE-IOT-0034 | inventory | A topology and dependency map shows devices, their peers, protocols and Purdue levels, and answers which devices depend on a given device. | <https://developer.cisco.com/docs/cyber-vision/#!maps> |
| AE-IOT-0035 | threat | Tenant threat indicators (IP addresses, domains) with expiry are matched against device communication and raise threat-intelligence anomalies that raise risk. | <https://learn.microsoft.com/en-us/azure/defender-for-iot/organizations/how-to-work-with-threat-intelligence-packages> |
| AE-IOT-0036 | edge | The edge appliance keeps enforcing its last verified configuration when the cloud is unreachable, buffers observations in a bounded queue, and refuses tampered configuration. | <https://learn.microsoft.com/en-us/azure/defender-for-iot/organizations/how-to-manage-individual-sensors> |
